# Dakota Digital redesign prototype

Read this at the start of every session. Update the "Status" section at the end of each one. The shared rules in `../CLAUDE.md` apply too.

## What this is
A working mock-up of dakotadigital.com (Dakota Digital makes gauge clusters for classic cars, trucks and motorcycles). It is built from the "Dash Finder" design (`Dakota Digital Dash Finder.pdf` and the design export `.html` in the repo root) and the live site's content. It is a prototype to show the client, not the live store: cart, checkout and accounts still link to dakotadigital.com.

- Preview: https://dakotadigital-ten.vercel.app/
- Repo: https://github.com/couchju1/DakotaDigital (public)
- Product names, photos and the logo belong to Dakota Digital, Inc. Don't publish it as theirs without their approval.

## Stack
- Plain HTML, CSS and JavaScript in `redesign/`. No framework and no build step on deploy.
- Most pages are generated by Python scripts in `tools/`. `redesign/README.md` lists which pages are hand-built (`index.html`, `camaro-1969-rtx.html`, `dealers.html`) and which are generated. Edit the script or `tools/content/*.json` for generated pages, then run `python tools/build_pages.py` from the repo root. Never hand-edit a generated page: the next build overwrites it.
- `redesign/shop/` (212 category pages, 811 product pages) is written by `tools/build_catalog.py` from a crawl cache of the live site. The cache is not in the repo. The full pipeline (crawl, build, images, verify) is in `redesign/README.md`.
- Forms (signup, contact, install quote) post to `api/submit.js`, a Vercel serverless function that inserts into `form_entries` in the Neon project `dakotadigital-forms`, as the insert-only role `web_forms`. It reads `DATABASE_URL` from the environment.
- Dash Builder (`dash-builder.html`) with a Three.js 3D pilot for the 1969 Camaro. Three.js and esbuild are pinned in `package.json` and vendored into `redesign/js/vendor/three/` by `npm run vendor:three`. No CDN. `docs/dash-builder-notes.md` covers the builder, its data sources, URL parameters and the rules for the 3D model.
- Shared front-end files: `styles.css` (tokens at the top), `garage.js` (My Garage plus the one copy of fitment data), `dash-finder.js`, `fit.js`, `shop.js`, `buy-dock.js`, `builds.js`, `search.js`.

## Run it locally
- `npm install` (needed for the copy lint and for re-vendoring Three.js).
- `python tools/build_pages.py` after any change to generated pages or `tools/content/`.
- Serve: `python -m http.server 5178` from `redesign/`, then open http://localhost:5178. Forms fail here because there is no `/api`. To test forms, use `npx vercel dev` with `.env.local`, or the preview URL.
- `npm run lint:copy` checks every description rewrite. It must pass before any deploy.

## Deploy
- Live branch: `main`. Hosted on Vercel (`vercel.json`), which serves `redesign/` as-is (`buildCommand` empty). A push to `main` publishes in a few minutes.
- Vercel needs `DATABASE_URL` in Project Settings > Environment Variables. Locally it lives in `.env.local` (git-ignored by `.env*`).
- This site is not on Hostinger. Don't move it without asking.
- Work on a branch for anything non-trivial. Don't push to `main` until I say so. After a push, tell me whether it went live and how you checked (for example `curl -sI` the preview URL and load the changed page).
- Read form entries in the Neon SQL editor: `SELECT * FROM form_entries ORDER BY created_at DESC;`

## Rules
- Never invent a fact about the business. Content comes from the live site. If something is missing, ask me or leave it out.
- Product description rewrites live in `data/descriptions/`. File naming (`<main sku>.md`, `<main sku>-p<id>.md`, `p<id>.md`) is explained in `redesign/README.md`. `REVIEW.md` and `REVIEW-FIXES.md` there trace every fact to its source.
- No secrets in git. `DATABASE_URL` goes in `.env.local` (git-ignored) or in Vercel's settings.
- The repo is public on GitHub. Don't commit anything private.
- Don't add dependencies or scripts without telling me why.
- For any work on how the site looks, its layout, motion or interactions, load the `ui-ux-pro-max` skill first (skip it for data, crawl or API work). Its suggestions are recommendations: the existing `styles.css` tokens and the client's real content come first, and don't add anything it suggests without asking.

## Search engines
- `site.config.json` has `"indexable": false`. While it is false, every page is `noindex`, `robots.txt` disallows everything and `vercel.json` sends an `X-Robots-Tag: noindex` header.
- Leave it false until I say the site is launching. The launch steps are in `redesign/README.md` (set it true, then rebuild with `build_catalog.py` and `build_pages.py`; that drops the noindex tag, the robots.txt block and the header).

## Key decisions and why
- **Static HTML, no framework.** It is a prototype that has to load fast on Vercel with no build step, and the client's content is mostly a catalog. The Python generators give one shared header/footer without a framework.
- **Catalog rebuilt from a crawl of the live site** (with the owner's permission for the price/option steps). Real prices, SKUs, options and photos make the prototype credible, and `tools/verify_catalog.py` proves every page matches the live one (last run: 0 failures across 212 categories, 811 products, 9,771 images).
- **One copy of fitment data** in `garage.js` (`PLATFORMS`, `SERIES`, `yearsOf`). The finder, My Garage, `fit.js` and the Dash Builder all read it, so they can't disagree. `dash-builder-data.json` holds product details only, never fitment.
- **Description rewrites are separate files with a lint**, so rewritten copy can be checked for copied phrasing, word count and banned words, and the originals stay untouched in the crawl.
- **3D is a progressive extra.** It loads only for the 1969 Camaro, with WebGL, without reduced motion, and only after the first scroll, tap or key. Everything works without it, and a stand-in car is drawn if the model fails.
- **Three.js vendored, not from a CDN**, so the page has no third-party script dependency and the version is pinned.
- **Forms write to Neon through an insert-only role**, so a leaked connection string can't read or delete entries.
- **noindex until launch**, so the prototype never competes with the live site in search.

## Known issues and limits
- Dealers on `dealers.html` are placeholder data from the design (12 shops, ZIP 57107 only). Other ZIPs link to the live locator.
- Finder fitment (which years get which series) comes from the design file and still needs checking against the live site.
- Add to cart only confirms the selection and links to the live product. Install quote requests are saved but not emailed to shops.
- `track()` in `dash-builder.js` is a no-op. Analytics not wired (ask before adding any tracking).
- 3D view exists only for the 1969 Camaro. Other cars show "3D view is coming for more cars."
- HDX for the 1970-81 Camaro has no product page, so the Dash Builder leaves it out.
- One live image 404s on the source site (`img/cup-4001.gif`).
- 185 rewrites are marked `short:` because the live page has too little to say. `REVIEW.md` has 115 `FLAG` lines and `REVIEW-FIXES.md` has its own flagged list, waiting for a human look.
- Lighthouse mobile is about 85: Google Fonts CSS and `styles.css` block rendering on every page.
- Catalog content is a snapshot from October 2026. Re-crawl and run `verify_catalog.py --refetch N` before showing it if the live site may have changed.
- The source `.blend` for the Camaro model (127 MB, CGTrader item 6761347) is not in the repo. See `docs/dash-builder-notes.md` to rebuild the `.glb`.
